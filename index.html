Upgrading from 1.1

  1. Back up litehcp.db.
  2. Replace litehcp.php and open it. The database migrates itself on first load, and existing HCPs get tiers and deciles.
  3. Users with the old user role become editors. Audiences saved as filters keep working.
  4. Run the self-test to check the install.

One intentional change: exports now leave out Do Not Contact HCPs, so the 1.1 sample segment "Suppression list (Do Not Contact)" exports no rows. Use the Suppression page to review them instead.

Privacy is the default, not a setting

HCP data is regulated data. LiteHCP is built so the safe path is also the easy path.

  • Your server, your data

    Everything lives in a SQLite file next to the app. Nothing is sent to a vendor cloud — there is no vendor cloud.

    sqlite:./litehcp.db

  • Suppression you can't bypass

    Do Not Contact and suppression-list HCPs are excluded inside every count, preview and export, with no override for any role.

    applied in every query

  • Minimal exports by default

    Exports ship IDs, specialty, region, persona, tier and scores. Email and name appear only for consented HCPs, when an admin enables PII export.

Questions, answered

Configuration, the rules JSON reference and security details are in the documentation.

Does any data leave my server?
No. The app is a single PHP file using a local SQLite database. There are no analytics, no phone-home, and no external APIs in the data path. Since 1.2 the app also loads no third-party fonts or scripts, so it works fully offline.
What do I need to run it?
PHP 8.0+ (8.3 or newer recommended) with PDO and SQLite enabled, standard on virtually all shared hosting, plus write permission in the app folder. That's the entire requirements list — no MySQL, no Composer, no Node.
Can it handle large HCP lists?
Imports run in short background chunks with a progress bar, so shared-hosting time limits aren't a problem, and a cron job recomputes scores, rules and tiers in batches for large datasets. SQLite comfortably handles hundreds of thousands of profiles for this workload.
How do the targeting rules work?
Each rule is "when these conditions are true, then update the HCP". Build it from dropdowns or write it as JSON: conditions joined by all or any, with operators like =, >=, in, contains and regex, and actions that set a persona, add tags, set a compliance flag or adjust the priority score. Rules run in the order you set, each profile keeps a trace of which rules fired, and audiences can target by that trace.
Is the scoring configurable?
Yes. Tier cut-offs and planned calls per tier are in Settings. Priority weights (consent / recency / engagement), the recency window, confidence penalties, imputation defaults, export formats and rate limits are in a clearly-marked config block at the top of the file, with a few common settings overridable via .env.
How does suppression work?
An HCP is excluded if it is on the suppression list or an enrichment rule gives it the Do Not Contact persona. The exclusion is part of every count, preview and export query, so it can't be switched off for one audience or one user. You can paste in IDs that aren't imported yet; those HCPs are excluded the moment they arrive.
I'm on 1.1. How do I upgrade?
Back up litehcp.db, replace litehcp.php, and open it. The database migrates itself, existing HCPs get tiers and deciles, and filter-based audiences keep working. Then run php litehcp.php action=selftest. See upgrading from 1.1 for the one behavior change.
What does it cost?
Nothing to deploy — it runs on infrastructure you already have. There are no per-seat licenses, no usage fees, and no contracts. The source is on GitHub.
