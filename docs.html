#Deploy on shared hosting (cPanel / Namecheap)

Requirements: PHP 8.0+ (8.3 or newer recommended) with PDO + SQLite (default on nearly every host), and write permission in the app directory.

# 1. upload the single file
public_html/litehcp.php

# 2. cPanel → MultiPHP Manager → set directory to PHP 8.3+ (8.0 minimum)

# 3. permissions
litehcp.php        0644
app folder         0755
litehcp_uploads/   0750   # created automatically; 0755 if your host requires it

# 4. enforce HTTPS (hosting panel or redirect rule)

# 5. visit /litehcp.php → register → first user becomes admin

# 6. optional: check the install
php litehcp.php action=selftest   # 43 checks, throwaway database

On first load the app auto-creates its SQLite schema at ./litehcp.db and the litehcp_uploads/ directory (with web access denied via .htaccess).

See it working immediately: Overview → Load sample data loads the embedded demo dataset in one click — 200 realistic HCP profiles with believable data gaps, 9 enrichment rules, and 6 audiences. Same data as the browser demo.

#Upgrading

From 1.1:

# 1. back up
cp litehcp.db litehcp.db.bak

# 2. replace litehcp.php, then open the app once
#    schema migrates itself (PRAGMA user_version 0 → 2)

# 3. check
php litehcp.php action=selftest
  • New columns (npi, tier, priority_decile), the suppressions table and export history columns are added; existing HCPs get tiers and deciles on first load.
  • Users with the old user role become editors.
  • Audiences saved as filters (sql_filter) keep working and are re-validated on every use; rule-based audiences open in the new builder.

Behavior change: exports now always leave out HCPs with the Do Not Contact persona or on the suppression list. The 1.1 sample segment "Suppression list (Do Not Contact)" therefore exports no rows; use the Suppression page to review those HCPs.

From 1.2.0 to 1.2.1: replace litehcp.php; the database is unchanged. Then run Settings → Maintenance → Recalculate all scores and rules once (or the cron job) to clear personas, tags and “cleared to contact” flags left behind by earlier rule edits. See the changelog for the fixes.

#Run locally

$ git clone https://github.com/tanzir71/litehcp_targeter
$ cd litehcp_targeter
$ php -S localhost:8000
# → open http://localhost:8000/litehcp.php

The built-in PHP server is fine for evaluation and development. For production, use any real web server with HTTPS.

#CSV import

Import is a four-step flow: upload → match columns → check data → import. Nothing is written to the database until you start the last step.

  • Upload — CSV only, validated by extension, MIME type, and size (UPLOAD_MAX_BYTES). Filenames are sanitized and files stored in litehcp_uploads/.
  • Match columns — columns are matched to internal fields automatically, first by exact name, then by common synonyms (for example NPI, Customer ID → HCP ID, First name + Last name → full name, Email opt-in → email consent, Last seen → last activity). Each column shows an example value and how it will be read; change any match, skip a column, or keep it as a custom field. Internal fields: hcp_id, npi, name, email, specialty, region, organization, role, consent_email, consent_web, last_activity_ts, imports_count. A mapping-confidence figure feeds the profile confidence score.
  • Check data — every row is scanned: missing HCP ID or name (skipped), duplicate IDs (later row wins), NPIs that fail the Luhn check digit (kept without NPI), unreadable dates and unrecognized consent values, with row examples and counts of new versus updated HCPs.
  • Import — runs in the background in short chunks with a progress bar (a button continues it without JavaScript). Profiles upsert by hcp_id, so re-imports are safe: columns a file doesn’t have keep their current values (a consent-only update leaves specialty and activity alone), a known NPI is kept when a later file has none, and the HCP is scored on the merged record.

Values are read flexibly: dates as 2026-09-14, 09/14/2026, 14.09.2026 or Unix seconds/milliseconds; consent as 1/0, yes/no, true/false, opt-in/opt-out or granted/withdrawn.

#Imputation

Each matched field that has blank values in the file gets an imputation strategy, chosen on the Match columns step:

StrategyBehavior
fixedSubstitute a constant (e.g. region → "Unknown").
modeUse the most frequent value in the file for that column.
meanUse the column mean (numeric fields).
leave_null_flagKeep it null, but flag the profile as incomplete.

Imputed values are stored in the profile's metadata and shown with a dotted underline throughout the UI — imputation is never silent.

#Scoring

Priority score (0–100)

priority = 100 × ( 0.30 × consent01      # (consent_email + consent_web) / 2
                 + 0.40 × recency01      # 1 − age/recencyWindow, floored at 0
                 + 0.30 × engagement01 ) # imports_count / 10, capped at 1

Rules may then adjust it (add_priority_delta) or set it outright (set_priority_score). The final value is clamped to 0–100.

Confidence score (0–100)

Starts at 100 and is reduced by missing required fields, missing optional fields, imputed fields, and incomplete column mapping. Audiences can require a minimum with a Data confidence condition.

Tiers and deciles

After scoring, every HCP gets a tier (A from 80, B from 50, otherwise C; cut-offs editable in Settings) and a priority decile from 1 to 10 across the whole database (10 = top 10%). Tiers drive planned calls per cycle in CRM exports. Both refresh after imports, rule changes, Settings changes and cron.

Each HCP's page explains its score: the consent, recency and engagement points, then each matching rule's change in run order, and the resulting tier.

#Rules reference

Rules are built in a When/Then editor (conditions, then actions) and stored as JSON, evaluated against every profile in run order (top of the list first; move rules up or down on the Rules page). The JSON view supports everything the editor does plus nested groups. A rule is a condition tree plus actions:

{
  "match": "AND",                     // or "OR"; nested "all"/"any" arrays also supported
  "conditions": [
    { "field": "specialty", "op": "=",  "value": "oncology" },
    { "field": "consent_email", "op": "=", "value": 1 }
  ],
  "continue_on_match": true           // false = stop evaluating further rules
}
OperatorsActions
= · != · > · >= · < · <= · in · contains · regex set_persona · set_priority_score · add_priority_delta · set_compliance_flag · add_tags

The special field tags matches against tags added by earlier (higher-priority) rules, so rules can chain. Every matched rule is recorded in the profile's metadata trace — segments can target "profiles where rule X fired".

Test before saving: the rule editor re-runs every rule with the draft in its place and shows how many HCPs match, how many would change, and who would become excluded or no longer excluded, with before/after examples. Each run starts from a clean slate, so a persona, tag or “cleared to contact” that a rule no longer gives is removed. Saving re-applies all rules automatically (up to 20,000 HCPs; larger databases use Re-apply or cron).

#Audiences

An audience is a list of conditions joined by all or any, built by pointing and clicking. The count updates after every condition, and a funnel shows all HCPs → matching → always excluded → ready to use, with the tier mix and the ten highest-priority HCPs.

ConditionOptions
Specialty, region, role, organization, persona, tieris any of / is none of
Reachable byany of / all of: email, web (from consent)
Priority score, priority decile, data confidence, engagement countat least / at most / exactly
Last activitywithin / not within the last N days
Tag, enrichment rulehas / lacks tag; rule was / was not applied
Custom fields (from imports)number or text comparisons

Definitions are validated against this allowlist and every value is quoted or cast before it reaches SQL, so no user-written SQL runs. Suppression is always applied on top (see below).

Audiences saved as filters in 1.1 keep working. Their filters are still strictly validated (allowlisted fields; semicolons, comments, double quotes and DDL/DML keywords rejected) and still honor the strict/inclusive confidence modes:

-- 1.1 filter examples
specialty = 'oncology' AND confidence_score >= 70
consent_email = 1 AND region = 'West'
imports_count >= 5

#Campaign planner

Every saved audience has a plan panel: set contact rate, response rate, cost per contact and value per response, and see projected contacts, responses, cost, value and ROI update as you type, alongside planned calls per cycle by tier. Saved plans are stored with the audience and in the audit log with their assumptions, so the numbers behind a plan stay traceable. (The 1.1 simulator link opens this panel.)

#Suppression

An HCP is excluded when it is on the suppression list or an enrichment rule gives it a suppression persona (Do Not Contact by default). Exclusion is part of every audience count, preview and export query. It cannot be switched off for an audience, a format or a role.

  • Admins add HCP IDs on the Suppression page (paste a column from a spreadsheet) with a reason: opted out, AMA PDRP restriction, deceased or retired, legal or compliance hold, or other.
  • IDs that aren't imported yet are kept, so those HCPs are excluded the moment they arrive.
  • Each HCP page says why it is excluded; additions and removals are audited.

#Roles

RoleCan
ViewerSee the Overview, HCPs (emails hidden), audiences, rules, imports and exports history.
EditorEverything a viewer can, plus import, build rules and audiences, save plans, export minimal and CRM formats, read the audit log.
AdminEverything, plus suppression, settings, people and roles, deleting rules and audiences, and email platform exports when PII export is on.

The first account is an admin. Registration is closed by default; admins add people in Settings. Role changes apply on the next page load.

#Exports & privacy

FormatFieldsWho
Minimal CSVhcp_id, specialty, region, persona, priority_score, confidence_scoreEditors and admins
CRM target listhcp_id, npi, tier, planned_calls, specialty, region, persona, priority_scoreEditors and admins
Email platformhcp_id, name, email, specialty, persona, tierAdmins, with export_pii on; only HCPs with email consent and an address
  • The default format has no email, no name. Suppressed HCPs are never written to any file.
  • Field selection is enforced against allowedExportFields server-side; text cells that could run as spreadsheet formulas are neutralized.
  • Every export is audited with its format, row count and excluded count, and listed on the Exports page. Files are generated on demand and not stored on the server.
  • Exports are rate-limited.

#Cron recompute

For large datasets, recompute base scores and re-apply rules on a schedule instead of synchronously:

# cPanel → Cron Jobs (CLI form, preferred)
php /home/USER/public_html/litehcp.php action=cron_recompute token=YOUR_CRON_TOKEN

# or via HTTP
https://your-site.com/litehcp.php?action=cron_recompute&token=YOUR_CRON_TOKEN

Set the token via .env (CRON_TOKEN) and rotate it if it leaks; the default CHANGE_ME is refused. Processing is batched (200 profiles per transaction), and tiers and deciles are refreshed at the end. Settings shows the exact command for your server.

#Security model

  • Auth — password hashing via password_hash, session regeneration on login, idle timeout, first user becomes admin, registration closed by default afterward. Roles (viewer, editor, admin) are checked server-side and re-read from the database on every request.
  • CSRF — token required on every POST; the JSON endpoints used by the builders accept it in an X-CSRF-Token header.
  • Headers — CSP (nonce-based script, no third-party origins at all), X-Frame-Options DENY, nosniff, referrer policy, permissions policy.
  • SQL — prepared statements everywhere; audience builder values quoted against a field/operator allowlist; 1.1 filters validated against a field allowlist with keyword denylist.
  • Suppression — applied inside every count, preview and export query, with no override.
  • Uploads — CSV-only validation by extension/MIME/size, sanitized filenames, uploads directory denied to the web.
  • Rate limiting — login, registration, and export endpoints.
  • Errors — logged server-side; no stack traces to the browser.
  • Self-test — php litehcp.php action=selftest verifies suppression, export formats, builder quoting and the role matrix on a throwaway database.

Hardening checklist for production: enforce HTTPS, use a strong admin password, consider an .htaccess IP allowlist or basic auth in front, and make sure litehcp.db is not world-readable. Full details in SECURITY.md.

#Backups

The entire state is two artifacts next to the app file:

litehcp.db          # all data — back up daily/weekly
litehcp_uploads/    # original CSVs + server logs — optional

Restoring is copying the files back. There is no external state.
